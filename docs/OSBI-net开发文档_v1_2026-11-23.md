## 1. 产品目标与迁移目标

### 1.1 产品定位

OSBI-net 是“多 node（分布式抓取）+ 单 server（统一本体/图谱构建与存储）”的标准化产品，可复制给同类型的基层政府部门客户。

- **node**：一个 client 实例，负责抓取、去重、提交材料、生成报告。
- **server**：统一相关性判断、本体提取、图谱存储、证据查询。
- **channel**：话题/相关性单元，全局共享，所有 node 均可提交与查询；node 只是把信源归类到某些 channel。
- **schema**：每个 channel 绑定的本体类/谓词；policy 家族共享一套 schema，economy 独立。
- **rules**：提取特例规则、内容分类、时间窗、质量门禁；由 server 按 channel 应用。
- **statement**：server 维护的 channel 级相关性说明，注入 relevance prompt；**不是 node 上传的 focus**。
- **report board**：node 本地的报告板块，拥有自己的 purpose/focus、query、属地偏好和本地过滤 rules。

### 1.2 迁移工作目标（必须记住）

本轮分**双线期**与**最终切流**两个阶段。

#### A. 双线期（一段时间内）

1. **旧正式报告继续，但旧栈精简**：`~/midplatform/run_all.sh` 保留 `schedule_task` 与旧 `wiseflow_server`/`wiseflow_backend`，并做以下调整：
   - **停掉 wiseflow acquisition**（旧抓取，避免与 osbi client 重复抓取）；
   - **停掉 ontology batch**；旧 `wiseflow_server` 切 `LEGACY_INFO_ONLY=1`（不再做本体）；
   - `schedule_task` 只跑旧版 `weeklyreport` 与 `topnews`，推两个正式群；
   - 保留每日 info 同步 QAnyThing 库、以及删除 QAnyThing 库等量内容的逻辑；
   - **移除**原有影子 topnews / 影子 weekly 任务（改由 osbi client 承担）。
2. **本地 osbi client 以独立进程运行**（不放进 `run_all`）：作为 node 接入远端 server，生产图版 topnews / weeklyreport，发测试群，取代原来的影子任务。
3. **云端 OSBI server 不做 info**：只做 channel 相关性判断 + 本体图；旧报告所需 info 由本地旧管线产生。
4. **本地新增独立 legacy bridge 进程（不属于 osbi-net 开源仓）**：从 OSBI client 的本地缓存/outbox 读取 material，转成旧 v3 请求提交给本地旧 `wiseflow_server`（info-only）；旧 8077、旧 topnews/weekly、QAnyThing 链路保持不变。
5. 接入成都狮子山 node，两个 node 共用同一云端 server、全部 channel 开放。

#### B. 最终切流

双线验收通过后：停掉旧生产内容（`schedule_task` / `wiseflow_server` 及老报告），osbi client + 远端 server 正式成为生产；之后按需退役旧组件。

“完美复现”按**稳态口径**验收：功能、输出格式、板块结构、推送形态一致；零历史导致首周周报/惩罚/覆盖历史偏薄，预热 N 周后与旧影子稳态输出对齐。

### 1.3 本轮非目标

- 不做 tenant/订阅/按 channel 授权（全部 channel 对所有 node 开放）。
- 不做历史图迁移、不做旧 focus 数据兼容。
- 不做 channel 的动态自动创建；channel 由运维配置。
- 不在 `~/osbi-net` 开源仓内实现 legacy 兼容；`~/midplatform` 的改造仅限第 12 节双线期兼容范围。

## 2. 术语与不变量

### 2.1 不变量（实现时不得破坏）

1. **Server 独占相关性判断与本体提取**；node 不提交任何相关性文本（无 focus/focuspoint）。
2. **全部 channel 对所有已认证 node 开放**；没有订阅、没有 channel ACL。node 身份只用于 provenance、`sourceScope=own` 和质量统计。
3. **node 采集阶段的本地预筛只做本地去重**（URL/内容缓存）；不引入 Jev、不做相关性判断。
4. **下游报告查询后的本地过滤允许 Jev**；可配置开关，关闭时使用 client 配置的 LLM 判断。
5. **evidence 默认 `sourceScope=all`**：查本 server 内所有 node 贡献的该 channel 内容；`own` 为可选。
6. **属地偏好是查询时声明的参数**（`territoryPreference` + `territoryMode`），不是写死的 node 全局硬过滤。必须允许临时查其他地区（如临汾学习成都经验）。
7. **同一 schema 的 channel 共享一个图存储**；channel 是 provenance/查询过滤键。node_id 只做溯源，不做数据隔离。
8. **channel statement 是跨地市、跨客户的话题级宽口径**；具体子主题/属地差异放在 node 的 board query/local rules。
9. **配置外置**：channel/statement/schema/seeds/node 等是部署配置，代码仓只放 example；代码中不得硬编码具体 channel、板块名、上海/成都地名。
10. **零历史起步**：不做图/覆盖历史/惩罚账本迁移。
11. **OSBI server 不做 info**：云端 server 只做 channel 相关性/本体图；旧报告所需 info 由本地旧管线（info-only 8078）产生。**OSBI client 不 legacy 特例改动**；兼容逻辑全部放在独立的 legacy bridge（midplatform 侧）。

### 2.2 关键术语对照

| 旧概念 | 新概念 |
|---|---|
| focus / focuspoint | **channel + channel.statement**（server 侧）；node 侧只保留 report board 的 purpose |
| focus_id → board_label | **channel → board/title** |
| ontologyLibrary/focus 路由 | **channel 显式指定** |
| 一个信源一个 focus | **信源 → 一个或多个 channel** |
| 关注点组 | **node 的 source→channel 映射 + report boards** |

## 3. 架构与数据流

```
node A ─┐   source → channel(s)
node B ─┼─► POST /v1/channels/{channel}/materials
node C ─┘        │
                 ├─ auth：node key → node_id（全部 channel 可用）
                 ├─ dedupe：materialHash = 内容 + channel
                 │    同一内容同 channel 多 node 提交 → 一个 job，多 node provenance
                 ├─ relevance：channel.statement + channel.rules + 发布日期窗口
                 │    → blockIds / linkIds（node 不提供 focus）
                 ├─ ontology：channel.schemaRef + channel.rules
                 │    provenance: channel, node_ids, url, published_date, content_type...
                 └─ store：policy-family 共享 policy 图；economy 独立图
                          ▲
node 报告链路 ───────────┘
  board.purpose/focus
    → query：channel + sourceScope(all) + territoryPreference + 日期/文本/实体
    → server evidence
    → 本地过滤（可选 Jev / client LLM / 确定性规则）
    → 影子选材 → 写作 → docx/推送
```

## 5. 发布日期窗口规则（`policy-latest`）

### 5.1 配置

channel 配置：

```yaml
- id: policy-latest
  title: 政策速递
  schemaRef: policy
  statement: "最近三天内发布的政策、政策公告、政策公示、政策解读、规范性文件、实施意见、规划纲要及配套文件。"
  dateWindowDays: 3
  dateField: publishedDate
```

- 语义：**按发布日期/公布日期过滤，不是抓取时间，也不是内容里提到的年份。**
- 这是**入库相关性门禁**，不是查询门禁。窗口内发布的内容进入图后永久保留；以后查询只要日期范围覆盖到即可查到。
- 查询的 `fromDate/toDate` 是另一个概念，不会重新执行 3 天门禁。

### 5.2 发布日期判定顺序（server 确定性逻辑）

新增模块建议：`server/wiseflow_server/publication_date.py`

1. **`meta.publishedAt`**（抓取时从源页面/公众号元数据取得）→ `dateSource=meta`
2. **标题中的显式日期**：客户端已在标题拼接 `（内容发布日期：YYYY-MM-DD）`，或在标题中出现“发布日期/公布日期/印发日期/成文日期” → `dateSource=title`
3. **正文中的显式绝对发布日期**：在标题 + 前若干块中匹配带标签的日期：
   - `(发布|公布|印发|成文|签发|更新)日期\s*[:：]?\s*(YYYY-MM-DD|YYYY年M月D日)`
   - `内容发布日期\s*[:：]?\s*...`
   - 以及标题/正文开头的 `YYYY-MM-DD`、`YYYY年M月D日`、`YYYY/M/D` → `dateSource=body_absolute`
4. **正文中的相对发布日期**（见 5.2.1）：`发布于N天前`、`24小时前`、`昨天/前天` 等 → `dateSource=body_relative`
5. **无法从 meta、标题、正文判断，或只有模糊表达** → `dateSource=unknown|ambiguous`，**窗口 channel 直接拒绝**（不选任何 block/link）。
6. 若正文中多个显式绝对发布日期互相冲突 → `ambiguous`，窗口 channel 拒绝；绝对日期与相对日期冲突时，**绝对日期优先**并打 `date_conflict`。

**不得**用 `capturedAt` 顶替发布日期；`capturedAt` 只能作为相对日期换算的参考时间。不得把事件发生日（如“事故发生于3天前”）、正文提到的历史年份当作发布日期。日期统一 `normalize_publish_date` 为 `YYYY-MM-DD`。

### 5.2.1 正文相对发布日期规则

只把**处于发布日期/发布信息位置**的相对表达当作发布日期；事件发生时间明确不采用。

**A. 可识别的发布位置标记**（表达必须靠近这些标记，或在标题/开头元信息区）：
- 前缀：`发布(于|时间)?[:：]?`、`发表(于|时间)?[:：]?`、`公布(于)?[:：]?`、`更新(于|时间)?[:：]?`、`最后更新[:：]?`、`成文(于)?[:：]?`、`印发(于)?[:：]?`
- 后缀：`... (发布|发表|公布|更新)`
- 无标记但出现在标题或第一块开头、且内容明显是“相对发布时间”的，可按 `body_relative_low` 处理（低置信）。

**B. 支持的相对表达与换算**（参考时间见 C）：

| 表达 | 换算 | 窗口结果 |
|---|---|---|
| `刚刚` / `刚才` / `几分钟前` / `半小时前` / `几小时前` | 视为参考日当天（`dateEstimated=true`） | 窗口内 |
| `N分钟前` / `N小时前`（N 为数字或中文数字） | 参考时间戳减 N 分钟/小时，再取 `Asia/Shanghai` 日期 | 按日期判断 |
| `今天` / `今日` | 参考日 | 窗口内 |
| `昨天` / `昨日` | 参考日 -1 | 窗口内（3 天窗） |
| `前天` / `前日` | 参考日 -2 | 窗口内（3 天窗） |
| `大前天` | 参考日 -3 | **窗口外（拒绝）** |
| `N天前` / `N日前`（N 为数字或中文数字） | 参考日 -N | `N>=3` 拒绝 |
| `N周前` / `N个星期前` / `上周` | 明显超出 3 天 | **拒绝** |
| `N个月前` / `上个月` / `去年` | 明显超出 3 天 | **拒绝** |
| `N天以前` / `N天之前`（开放式“以前/之前”） | 可能是 N 天或更久 | **视为 unknown，拒绝** |
| `近日` / `日前` / `近期` / `不久前` / `前段时间` / `早些时候` / `几天前` | 无法精确判断 | **视为 unknown，拒绝** |

- 中文数字（一/二/两/三/四/五/六/七/八/九/十/十一…/二十四）与阿拉伯数字都要支持；`半天前` 按 12 小时估算并标 `dateEstimated=true`。
- `N小时前` 先换算为时间戳再取日期，不能简单按“N/24 天”四舍五入；跨越午夜时以 `Asia/Shanghai` 日期为准。
- `近三天`、`最近三天` 这类是窗口描述，不是某条内容的发布日期；除非明确带“发布/公布”标记，否则不作为日期证据。

**C. 相对日期的参考时间**：
1. 如果已经找到**绝对发布日期**（meta/标题/正文显式绝对日期）→ 绝对日期优先，相对表达忽略（冲突时打 `date_conflict`，不因相对表达单独拒绝）。
2. 否则，如果存在页面级日期（meta.publishedAt 已在第 1 步使用）→ 以它为参考。
3. 否则使用 `meta.capturedAt`（抓取时刻）作为参考，`dateConfidence=medium/low`。
4. `capturedAt` 也缺失，且只有相对表达 → `unknown`，窗口 channel 拒绝。
5. `dateReference` 记录为 `absolute | meta | capturedAt`；相对换算结果落在未来日期（`age < -1`）→ `date_invalid`，拒绝。

**D. 冲突与质量**：
- 多个相对表达互相冲突且相差 >1 天 → `ambiguous`，拒绝。
- 相对表达换算结果与绝对日期冲突 >1 天 → 绝对日期优先，打 `date_conflict`；不据此拒绝。
- `刚刚/几分钟前/几小时前/半天前` → `dateEstimated=true`；`publishedDate` 记为参考日（或换算日），供查询排序，但打 `date_estimated` 质量标记。
- 所有相对表达命中的条目记录 `dateSource=body_relative` 与原始表达式 `dateExpression`，便于审计。

### 5.3 窗口计算

- 以抓取处理时刻 `now` 的 `Asia/Shanghai` 日历日为准。
- `age = (today - publishedDate).days`；`publishedDate` 可为绝对日期或相对表达换算出的日期。
- 命中窗口：`0 <= age < dateWindowDays`（即“最近 3 天” = 今天、昨天、前天；与现网 `age >= window` 拒绝逻辑保持一致）。
- `age >= dateWindowDays` → 拒绝（`三天前`、`大前天`、`72小时前` 在此被拒）。
- 相对表达换算依赖 `dateReference`；`dateEstimated=true`（刚刚/几小时前等）时仍按换算日期参与窗口判断，但保留质量标记。
- 未来日期：`age < -1` 视为可疑日期，窗口 channel 拒绝并打 `date_invalid`；`age == -1`（时区/跨日误差）可按未知处理，具体实现需加测试。

### 5.4 LLM relevance prompt 必须同步提示

`select_relevance` 的 system prompt 增加（与 channel 配置联动，不写死数字）：

> 本频道有发布日期窗口：asOf=YYYY-MM-DD，窗口为 [YYYY-MM-DD, YYYY-MM-DD]。
> 判断候选材料的发布日期时，优先使用标题/材料中明确标注的“内容发布日期/发布日期/公布日期/印发日期/成文日期”；其次使用正文中明确标注上述字样的日期。
> 正文中的相对发布时间（如“发布于3天前”“24小时前发布”“昨天发布”“前天发布”“更新于几分钟前”）只有在明确指向发布日期且能换算时才采用；“近日/日前/近期/不久前/几天前/2天以前”等模糊或开放式表达视为无法判断。
> 不要把事件发生日期（如“事故发生于3天前”）、正文提到的历史年份或发布日期以外的日期当作发布日期。
> 如果无法从元数据、标题或正文判断发布日期，**不得选择任何 block 或 link**；明显超出窗口的也不得选择。

- 时间窗信息与 channel statement 一起放进 relevance 调用的 user payload。
- relevance cache key 必须包含 channel id、statement 版本、窗口配置、asOf 日期。

### 5.5 确定性兜底

即使 LLM 选出了 block/link，server 在 `worker` 里仍需：

1. 用 5.2 的确定性逻辑计算发布日期；
2. 若窗口外或未知/歧义 → **清空 selection**（不写 info、不入 ontology queue、不递归链接）；
3. 记录 `reason=date_window|date_unknown|date_ambiguous|date_invalid|date_relative_vague`，返回空 selection + provenance/quality 标记；
4. 不把该材料作为 job failure（这是正常的门禁拒绝）。

对 catalog（只有 links、没有正文）：
- catalog 阶段不强制日期窗口；只按 statement 选链接；
- 文章正文抓取后再按 5.2/5.5 执行窗口门禁；
- 若 link 的 context/title 已有明确发布日期，可按该日期预筛，但不得用未知日期放行。

### 5.6 质量标记

窗口 channel 被拒绝时，可在响应/事件中记录 `date_window_reject`；非窗口 channel 缺日期则打 `no_date` 质量标记，不影响入图。

相对日期相关标记：
- `dateSource=body_relative` + `dateExpression`（原始表达）
- `dateReference=absolute|meta|capturedAt`
- `dateEstimated=true`（刚刚/几分钟前/几小时前/半天前）
- `dateConflict`（绝对日期与相对表达冲突 >1 天；绝对日期优先）
- `date_relative_vague` / `date_ambiguous` / `date_invalid`（拒绝原因）

### 5.7 测试用例

- meta 有日期且在窗口 → 入图；
- meta 有日期且超窗 → 拒绝；
- meta 无日期、正文有“发布日期：今天-2天” → 入图；
- meta 无日期、正文有“发布于3天前” → 拒绝（age=3）；
- meta 无日期、正文有“2天前发布” → 入图（age=2）；
- meta 无日期、正文有“24小时前” → 按 `Asia/Shanghai` 换算日期后入图；
- meta 无日期、正文有“72小时前” → 拒绝；
- “昨天/昨日发布” → 入图；“前天/前日发布” → 入图；“大前天发布” → 拒绝；
- “一周前/上个月/去年发布” → 拒绝；
- “近日/日前/近期/不久前/几天前/2天以前” → 视为 unknown，拒绝；
- “刚刚/几分钟前/几小时前发布” → 入图，标 `dateEstimated=true`；
- 中文数字“两天前”“二十四小时前”与阿拉伯数字行为一致；
- 事件相对时间“事故发生于3天前”不影响发布日期判断；
- 只有相对表达但 `capturedAt` 缺失 → 拒绝；
- 绝对日期与相对表达冲突 >1 天 → 采用绝对日期并打 `dateConflict`；
- 多个相对表达互相冲突 >1 天 → 拒绝（ambiguous）；
- 正文出现两个冲突的绝对发布日期 → 拒绝；
- 事件日期在窗口内、发布日期超窗 → 拒绝；
- 查询时用 `fromDate` 能查到窗口期入图的旧内容（验证“入库门禁 ≠ 查询门禁”）。

## 6. Node 配置

### 6.1 下游任务（board）配置模型

board 是 **node 本地的下游任务定义**，不是 server 概念。它决定这个报告任务：查哪些 channel、用什么 query/属地偏好、用哪种确定性选材算法、取回后如何本地过滤、写作意图和条数阈值。Server 只提供 channel 和 evidence；**新增一个下游任务只需要加一条 board 配置，不需要改 server 或代码**。

```jsonc
{
  "id": "party-building",
  "title": "基层党建",
  "channels": ["party-building"],       // 可多个
  "selector": "action",                  // candidates | action | policy | evidence
  "topN": 3,
  "minEdges": 4,
  "purpose": "……本地写作/选材意图……",
  "query": {
    "text": "",
    "entityUris": [],
    "contentTypes": [],
    "territoryPreference": ["上海市", "静安区", "临汾路街道"],
    "territoryMode": "prefer"            // prefer | only
  },
  "localRules": {
    "keywords": [],
    "excludeKeywords": [],
    "leaderBoost": true,
    "localityPenalty": true,
    "jev": "inherit"                     // inherit | on | off
  }
}
```

字段职责：

- `channels`：本 board 查询哪些 server channel（可多个）；不是订阅，也不改变 server 相关性。
- `selector`：本地确定性选材算法类型，取代旧的 `ACTION_BOARDS`/`POLICY_BOARDS` 硬编码；action 类板块用 `action`，政策链类用 `policy`。
- `purpose`：取代旧 focus，只用于本地写作与可选 Jev/LLM 判断，不上传 server 作为相关性依据。
- `query`：查询时参数（文本/实体/体裁/属地偏好）；可由配置固定，也可由 client LLM 根据 purpose 生成（v1 默认固定，parity 验收后再启用 LLM 生成）。
- `localRules`：evidence 取回后执行；默认值应等价于现有上海影子常量，保证临汾 parity。
- `topN` / `minEdges`：本 board 的报告条数与关系边阈值。

典型用法：

1. **同一 channel 服务多个 board**：成都 `community` → 民生服务 / 文明城市与环境；两个 board 用不同的 `query.text`/`localRules` 子主题过滤。
2. **一个 board 查多个 channel**（可选）：例如“党建引领”同时查 `party-building` + `community`；v1 默认为 1:1，需要时再配。
3. **临时跨区域学习任务**：临汾新增一个临时 board，`channels=["community"]`、`territoryPreference=["成都市","锦江区","狮子山街道"]`，即可专门学习成都经验；不需要 server 改动。
4. **新客户接入**：只需新增 node 的 source→channel 映射和 board 配置，server 的 channel 目录不变。

#### 6.1.1 board 实例 = 报告任务 × 板块

- `topnews` 与 `weeklyreport` 是**两个不同的下游任务**；每个任务的每个板块都是一个 board 实例。
- **临汾**：topnews 5 个（基层党建/经济动态/社区治理/数字社区/政策速递）+ weeklyreport 5 个（生产影子的 `select_weekly_focus` 默认也是这 5 个）= **10 个运行实例**。
- **成都**：topnews 7 个 + weeklyreport 7 个 = **14 个运行实例**（如果两个任务都用全部 7 个板块）。
- **不能用一个 weekly board 覆盖整个周报**：周报按板块分别选材、写作、记录覆盖历史；缺板块就少一节。

为避免 10/14 份重复配置，配置分两层：

```yaml
sections:                         # 共享定义：title / channels / query / territory / localRules
  - id: party-building
    title: 基层党建
    channels: [party-building]
    query: {...}
    localRules: {...}
  # ... 其余板块

reportTasks:
  topnews:
    boards:
      - section: party-building
        selector: candidates        # 每板块候选池 + 编辑 LLM
        topN: 3
        minEdges: 4
        purpose: "..."
  weeklyreport:
    boards:
      - section: party-building
        selector: action            # weekly 的 action-focus 选材
        topN: 2
        minEdges: 4
        purpose: "..."
```

- **Node 拥有一组 section 模板（每个板块一份），不是单个 board**；模板本身不被任务修改。
- 运行实例 = `section` + `task board override`（合并后的只读视图）。
- 同一 section 在两个任务中通常共享 `channels/query/territory/localRules`，差异在 `selector/topN/minEdges/purpose/prompt`。
- 覆盖规则：task board **只覆盖** `selector/topN/minEdges/purpose/prompt`；`channels/query/territory/localRules` 默认继承 section。若某任务确实需要不同的 query/localRules，定义一个新的 section（或显式整对象替换），**不做隐式深合并**，避免配置歧义。
- 某个板块不在某任务出现时，从该任务的 `boards` 列表省略即可。

`selector` 取值：

| selector | 用途 |
|---|---|
| `candidates` | topnews：逐板块构建候选池 + 编辑 LLM 精选 |
| `action` | weekly：action-focus（行动/机制/单位/政策关系网络） |
| `policy` | weekly：policy-chain focus（政策—行动链） |
| `evidence` | 通用手动选材：按查询条件直接取 evidence |

## 7. 协议与 API

### 7.1 鉴权与 node 身份

- 每个 node 一个 Bearer key；server 维护 key→node_id 映射。
- key 只做身份与 provenance；**全部 channel 开放**，不做 channel ACL。
- `nodeId` 由 key 推导，不信任请求体里的 nodeId；请求体可带 `nodeId` 仅用于校验一致性。
- 质量指标按 node_id 记录。

### 7.2 Material 协议 v4（`material-extract/v4`）

```jsonc
{
  "protocolVersion": "material-extract/v4",
  "channel": "community",          // REQUIRED，显式指定
  "nodeId": "linfen-shanghai",     // 可选，必须与 key 一致
  "requestId": "<64hex>",
  "materialId": "<64hex>",
  "input": {
    "title": "…",
    "blocks": [{"id":"B1","text":"…"}],
    "links": [{"id":"L1","text":"标题","context":null}]   // URL 不上送；client 本地 urlMap 还原
  },
  "meta": {
    "requestedUrl":"…","finalUrl":"…","canonicalUrl":"…",
    "author":"…","publisher":"…","publishedAt":"2026-11-20","capturedAt":"…",
    "adapter":"browser","textOnly":true,"mediaPending":false
  },
  "mode": "both"                   // only_link | both
}
```

变化：
- 删除 `focus`、`ontologyLibrary`；
- `channel` 必填，server 据此解析 schema/rules/statement；
- `materialHash` 包含内容 + channel（见 7.4）；
- OSBI server **不返回 `infos`**：server 只做选择 + ontologyJobs；旧报告所需 info 由本地 legacy bridge + 旧 8078 产生。

### 7.3 响应

```jsonc
{
  "protocolVersion": "material-extract/v4",
  "materialId": "…",
  "selection": {"blockIds":["B1"],"linkIds":["L1"]},
  "ontologyJobs": [{"blockId":"B1","id":"oq_…","status":"pending"}],
  "errors": [{"stage":"date_gate","blockId":null,"message":"date_window_reject"}]
}
```

- 日期窗口拒绝：`selection` 为空，`errors` 里记录 reason；不要用 5xx。
- `assignments`（如果有）只含 channel/provenance，不含 focus。
- 响应**不含 `infos`**。

### 7.3.1 info 不在 OSBI server

- OSBI server 只做 channel 选择 + 本体入队，不产出 info。
- 旧报告所需 info 由本地旧管线产生，链路见第 12 节“legacy bridge”：
  - 独立 bridge 从 OSBI client 本地缓存/outbox 读 material；
  - 转成旧 v3 请求提交到本地 `wiseflow_server`（8078，`LEGACY_INFO_ONLY=1`）；
  - 8078 只做选择 + info（Qwen/Qwen3-32B），不写 ontology；
  - 8077 `/list_info`、旧 topnews/weekly、QAnyThing 不变。
- OSBI client 不为该兼容链路增加任何特例代码。

### 7.4 内容身份

```text
materialHash = sha256(version, 内容, channel)
```

- 不含 nodeId/requestId/本机路径；
- 同一内容同 channel 多 node 提交 → 一个处理 job + 多个 node provenance；
- 同一内容不同 channel → 不同 job（各 channel 有自己的 relevance/statement）；
- processing revision（schema/rules/statement/model）由 server 另行判定 reuse/重提，不混入内容 hash。

### 7.5 Evidence 查询

`POST /v1/channels/{channel}/evidence`

```jsonc
{
  "sourceScope": "all",                 // all | own，默认 all
  "fromDate": "2026-11-17",
  "toDate": "2026-11-23",
  "territoryPreference": ["上海市","静安区","临汾路街道"],
  "territoryMode": "prefer",            // prefer | only，默认 prefer
  "text": "",
  "entityUris": [],
  "contentTypes": [],
  "excludeQuality": [],
  "cursor": "",
  "asOf": null,
  "limit": 100
}
```

- 必须显式指定 channel（路径或请求体）。
- `territoryPreference` 是**软偏好**：server 可作为排序/加权提示；`only` 才做硬过滤。无法判定属地的条目在 `prefer` 下保留，在 `only` 下排除。
- `sourceScope=own` 按 provenance 的 node_ids 包含当前 node 判定（不是“首次提交者”）。

响应 item 至少包含：

```jsonc
{
  "id":"…","channel":"community","board":"社区治理",
  "title":"…","text":"…","publishedDate":"2026-11-20","dateSource":"meta",
  "contentTypes":["news"],"qualityFlags":[],
  "sources":[{"nodeId":"linfen-shanghai","url":"…","publisher":"…","publishedAt":"…"}],
  "entities":[…],"relations":[…],"entityCount":6,"relationCount":4
}
```

### 7.6 Node 源与质量指标（仅记录，不做准入）

新增表 `node_source_metrics`（SQLite）：

```text
node_id, source_key, source_url, publisher,
first_seen, last_seen,
submissions, materials,
selected_blocks, selected_links,
extracted_blocks, entities, relations,
zero_relation_blocks, capture_failures
```

- `source_key`：规范化域名/公众号名/信源 id。
- 提交时累加 submissions/materials；选择/抽取后累加 blocks/entities/relations；client 可上报 capture failure。
- 提供运维只读查询；v1 不做拦截。

### 7.7 批处理与重提

- 夜间批处理沿用“选中原始块入队 → 批量提取”的模式；窗口由配置指定（初始 01:18–06:18，Asia/Shanghai）。
- schema/rules/statement/model 变化进入 fingerprint；提供按 channel/日期范围 reprocess。
- 不迁移历史图；reprocess 只针对新 server 已入库内容。

- 准备一批旧影子已处理的材料（同一日期、同一来源）。

### 11.3 功能验收

- 两个 node 均能：采集→提交→server 选择→入图→evidence→topnews/weekly→docx/推送。

- `sourceScope=own` 只返回本 node 贡献。

- 双线期：旧生产 topnews/weekly 继续推正式群；osbi client 独立进程的 topnews/weekly 推测试群；两者可并行对照。

1. **零历史**：新 server 新建数据目录，不导入旧图/覆盖历史/惩罚账本。
2. **部署 server**：按 handover 文档；7 channel、seeds、node keys、模型。OSBI server **只做选择 + 本体图，不做 info**。
3. **改造 client**：按第 9 节；先本地 dry-run（不推送）。**不为 legacy 链路增加任何特例代码**。
4. **双线期（一段时间）**：
   - 旧生产正式报告继续：旧 `schedule_task` 只跑旧版 weeklyreport/topnews、推两个正式群；保留 QAnyThing 同步 + 等量删除。
   - 停掉旧 `schedule_task` 里的 **wiseflow acquisition**（唯一会与 osbi client 重复抓取的部分）、ontology batch、影子任务。
   - 旧 `wiseflow_server` 8078 保留，但切到 **info-only 模式**（见 12.2）。
   - 旧 `wiseflow_backend` 8077、旧 topnews/weekly、QAnyThing 链路不变。
   - 新增独立 **legacy bridge**（见 12.1），从 OSBI client 本地缓存/outbox 读 material，转旧 v3 请求提交 8078。
   - 本地 osbi client **以独立进程运行**（不放进 `run_all`）：接远端 server，生产图版 topnews/weekly 发测试群，取代原影子任务。
   - 双跑对照：旧生产正式群 vs osbi 测试群；记录差异。
5. **最终切流**：双线验收通过后，停旧生产报告与 `schedule_task`/`wiseflow_server`；保留旧数据只读；osbi client 正式生产。
6. **退役**：客户确认后停老生产内容；删除过期内部文档（见第 15 节）。

### 12.1 legacy bridge（midplatform 侧独立进程，不属于 osbi-net 开源仓）

**输入**：OSBI client 本地状态库（`<client data dir>/client.db`）：
- 首选读 `outbox`：每行 payload 带 `channel`、blocks、links、meta、urlMap，且保留 `historyDays=30`；天然可按 channel 映射。
- `capture_cache` 作为兜底/补全（material 完整，但无 channel 字段，需要 source→channel 映射）。
- bridge **只读** client DB（WAL 并发读），不写 client 表、不改 client 代码/协议。

**处理**：
1. 只处理 Linfen node（本地实例）；成都 node 材料不进旧正式报告。
2. `channel → 旧 focus/task` 映射：
   - `party-building` → focus 10 / `#基层党建`
   - `economy` → focus 9 / `#经济动态`
   - `community` → focus 8 / `#社区治理`
   - `digital` → focus 12 / `#数字社区`
   - `policy-latest` → focus 11 / `#政策速递`
3. 把 v4 material 转成旧 `material-extract/v3` 请求：`focus` 用旧 focuspoint、`input` 用 blocks/links（旧 v3 Link 不含 URL）、`meta` 原样、`mode=both`、`ontologyLibrary` 按 economy/policy。
4. POST 到本地 `127.0.0.1:8078/v1/materials/extract`；不递归 links（链接遍历由 OSBI client 负责）。
5. bridge 自己维护消费状态（独立 SQLite/JSON），按 `(outbox id, channel)` 或 `materialId+channel` 去重；失败退避重试。

**同步时间**：OSBI client 抓取轮 12:18 / 23:18；bridge 在 **18:18 / 05:18**（Asia/Shanghai）各同步一次。

**缓存 TTL**（OSBI client 部署配置，不改开源默认代码）：
- 政府网站：`captureCache.defaultTtlSeconds` 建议 43200–86400（12–24h）；
- 政府域名可按 86400–172800 配置；
- `mp.weixin.qq.com`：604800（7d）或更长（1209600）；
- 这些是通用 TTL 配置，不是 legacy 特例。

### 12.2 旧 8078 info-only 模式

- 新增环境开关 `LEGACY_INFO_ONLY=1`：
  - 保留相关性选择 + `_info`；
  - **跳过** `ontology_queue.enqueue`、ontology batch、ontology engine 初始化；
  - 响应 `ontologyJobs=[]`；不写本地图。
- 旧 8078 info-only 的模型配置与现网生产一致：
  - info 主模型：`Qwen/Qwen3-32B`（`PERFORMANCE_MODEL`）；
  - 备用模型：`deepseek-ai/DeepSeek-V3.2`（`FALLBACK_MODEL`）。
- 视觉模型沿用现网同一套（client/browser 侧）：
  - 主：`Qwen/Qwen3-VL-32B-Instruct`；
  - 备：`Qwen/Qwen3-VL-30B-A3B-Instruct`；
  - extra：`zai-org/GLM-4.5V`。
- 云端 OSBI server 的模型配置不同，保持本文 10.2 / handover 的口径：
  - 相关性 `selected: deepseek-ai/DeepSeek-V3.2`；
  - 本体 `ontology: Qwen/Qwen3.5-27B`；
  - fallback `deepseek-ai/DeepSeek-V3.2`。
- 旧 8077 继续从 `data.db` 提供 `/list_info`；QAnyThing 上传/等量删除仍由旧 topnews 完成。
- 旧 `schedule_tasks` 不再注册 wiseflow acquisition / ontology_batch_task / shadow tasks。

## 13. 风险与待定项

| 风险/待定 | 处理 |
|---|---|
| 正文发布日期正则覆盖不足 | 先覆盖“发布/公布/印发/成文/签发日期”+常见格式；未知一律拒绝，不用 capturedAt 顶替 |

| 一源多 channel 抽取成本 | 主 channel 映射；综合门户限制 1–2 个 channel |
| 成都 seeds/领导规则缺失 | 首周可关闭 leader boost；补 seeds_chengdu；board 规则逐步校准 |
| 成都公众号精确显示名未提供 | 部署前向客户收集；mp 白名单必须精确匹配 |
| 现有 README/deploy 文档过期 | 以本开发文档为准；实现时同步修正 |
| pyproject server 入口错误 | 修正为实际 `wiseflow_server` |
| 零历史首周周报偏薄 | 验收按稳态口径；预热期标记 |
| 模型不一致导致 parity 失败 | 远端 server 与生产影子同模型/prompt/参数；否则只能功能等价 |
| bridge 读 client DB 的并发/清理 | 只读 WAL；优先读 outbox（保留 30d）；bridge 自维护消费状态，不写 client |
| 旧抓取未停导致重复抓取 | 双线期不注册 wiseflow acquisition；只保留旧报告/QAnyThing |
| 旧 8078 未切 info-only 导致重复本体 | `LEGACY_INFO_ONLY=1`；跳过 queue/batch/engine，验收检查 ontologyJobs 为空 |
| channel→旧 focus 映射错误 | 固定映射表 + 单测；成都材料过滤；对账旧报告板块 |
